# PGLife deployment preparation

No deployment, remote database connection, commit or push was performed. No production password is included. Only this PHP repository was edited.

## Manual alwaysdata setup

1. Select a PHP site and PHP **8.4** in alwaysdata. Enable `mysqli` with mysqlnd (`get_result` is used), sessions, and a private writable session storage directory. Use MariaDB **11.8**. Set `display_errors=Off`, `log_errors=On`, and keep PHP error logs outside the site. Configure HTTPS at the public frontend and origin. Do not rely on spoofable forwarded headers to decide whether cookies are secure.
2. Upload only runtime files: root PHP pages, `api/`, `includes/`, `css/`, `js/`, `img/`, favicon, and both `.htaccess` files. Exclude `.git`, docs, tests, database dumps, migration files, private configs and backups. Keep the actual public document root below `/home/pglife-shashwat/`, e.g. a dedicated application directory. Never set the document root to the account home. Verify Apache accepts the access rules; reproduce them in the host configuration if `.htaccess` is disabled.
3. Copy `config.example.php` to **`/home/pglife-shashwat/pglife-config.php`**, outside every public document root. Set the database password there privately, without putting it in commands, screenshots, logs, or source control. Restrict permissions to the account (normally `chmod 600`). Its host/name/username/port are already the intended values. The loader fails closed if the config is missing or inside this application root. An absolute `PGLIFE_CONFIG_FILE` environment variable may override its location; never populate it from an HTTP request.
4. Keep `base_path` as `/PGLife/` and `cookie_secure` as `true` for production. Cookies are host-only, HttpOnly, SameSite=Lax and limited to that path. Both the HTML base URL and server redirects use this fixed path. Decide the origin routing before enabling the proxy: either mount the origin at `/PGLife/`, or explicitly strip that prefix when forwarding to an origin mounted at `/`. A direct-origin installation mounted at `/` needs a separate configuration with `base_path => '/'`; it will not share the frontend's cookies.
5. Back up the selected `pglife-shashwat_pglife` database. For an existing schema, run `migrations/001_password_hash_capacity.sql` once. For a new database, use `DBMS/SQL queries.sql` in the already selected database. Do not run the top-level `CREATE DATABASE Pglife` statement on hosting. There are still seven tables. The only schema change is widening `users.password` from 100 to 255 characters to accommodate future `PASSWORD_DEFAULT` output. No migration runs automatically. Use an application DB account with only the necessary data permissions; run DDL separately.
6. Do not depend on dummy/sample accounts. Login accepts only `password_verify` hashes; **existing SHA-1 hashes cannot log in**. A hash cannot be converted without the original password. Register a fresh account for validation. If real legacy accounts exist, arrange a separately authenticated private reset or recovery process before enabling access. There is no public password-reset implementation. Do not blindly import the legacy dummy user data into production.
7. Enable durable edge/server rate limits for login and signup. The login session throttle (10 attempts per 15 minutes) is only supplemental and can be bypassed by starting another session. Validate existing duplicate emails/favorites before rollout. Signup uses a MariaDB advisory lock to serialize application registrations; favorite changes use transactions and a user-row lock. Database uniqueness constraints are absent in the original schema, so writes through other tools can still create duplicates. Keep InnoDB transactional tables.

Official references: [alwaysdata PHP configuration](https://help.alwaysdata.com/en/docs/web-hosting/languages/php/configuration/) and [PHP password_hash storage guidance](https://www.php.net/manual/en/function.password-hash.php).

## Local development

Copy the example to a private location outside the repository and all local webroots, e.g. a private folder in your home. Set local DB connection values there, `cookie_secure => false` for HTTP loopback only, and `base_path => '/'` when serving the repository as the root. Set `PGLIFE_CONFIG_FILE` to that absolute path in the local PHP process environment. For example, PowerShell can set `$env:PGLIFE_CONFIG_FILE` to the private file path and run `C:/xampp/php/php.exe -S 127.0.0.1:8080 -t .`. The example has an empty placeholder password and must be configured privately. Ensure PHP's `session.save_path` is writable. Do not expose the PHP development server to the network. Its router does not enforce Apache `.htaccess`, so keep it local.

## Required hosting and Netlify tests

- Configure the `/PGLife/` proxy rule before the portfolio SPA fallback. Preserve the remaining path, query strings, POST bodies and content types. Canonicalize `/PGLife` to `/PGLife/`. No portfolio repository or Netlify configuration has been edited here.
- In a real browser, verify each page, CSS/font/image, search form (including spaces, quotes and non-ASCII city names), carousel and AJAX URL stays under `/PGLife/`. Test direct deep links and refreshes. External fonts and Font Awesome still require third-party availability.
- Inspect the **frontend-domain** `Set-Cookie`: `PGLIFESESSID`, `Path=/PGLife/`, `Secure`, `HttpOnly`, `SameSite=Lax`, no origin `Domain`. Confirm the proxy forwards it and subsequent `Cookie` headers. Verify successful login rotates the ID, persists across pages/reloads, and dashboard works. Confirm a second browser cannot see another user's session.
- Verify anonymous dashboard and POST logout `Location` headers remain `/PGLife/index.php` on the frontend domain with the intended 302/303 status. Check the proxy does not rewrite them to alwaysdata or the portfolio root. Confirm logout deletes the cookie and the old session cannot access dashboard.
- Verify HTML and API responses are never cached/shared at Netlify or any intermediary, including logged-out pages containing CSRF tokens. Origin `Cache-Control: no-store, private` must survive; no forced caching override may apply. Verify static assets independently.
- Against a staging database on PHP 8.4/MariaDB 11.8, register a new account, check its stored hash is modern (without printing it), reject wrong passwords, log in, favorite/unfavorite, inspect counts/dashboard, and reload. Test duplicate signup, parallel favorite requests, missing/nonexistent properties, DB outage and advisory-lock support. Exercise invalid CSRF on authenticated requests. Confirm SQL-injection strings are treated as values and HTML-like names/descriptions render as text. Test phone, gender, long values and multibyte limits.
- Verify HTTP-to-HTTPS behavior, session storage permissions, inactivity expiry, generic PHP/DB errors, and that `/includes/`, SQL dumps, config files, `.git`, backups and test/migration directories cannot be downloaded. The private config must be unreachable by any served site.

Remaining risks: no durable account/IP rate limiting, no account verification or password recovery, original schema lacks unique constraints, and legacy accounts need an explicit recovery decision. Third-party frontend dependencies are old and have not been upgraded or audited here; a strict CSP/SRI policy remains future work. Cookie paths do not isolate the app from scripts on the same origin: the portfolio and any other frontend scripts on that host must be trusted. Proxy/session and DB integration checks above are release gates, not assumed successes.
